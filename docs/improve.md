## ۱. باگ‌های فانکشنال (Bugs)

### ✅ B-1 (رفع شد): کامنتِ «تایید خودکار» درست در صفحه نمایش داده نمی‌شود و باعث خطای JS می‌شود

**فایل‌ها:** `src/Front/View.php:325-327` (متد `render_single_comment_html`) و `assets/front/front.js:195-204`

> **وضعیت:** در `assets/front/front.js` رفع شد — انتخاب گره اکنون با `doc.body.querySelector('.user-comment') || doc.body.firstElementChild` انجام می‌شود (به‌جای `doc.body.firstChild`) تا Text Node ابتدای خروجی نادیده گرفته شود.

**توضیح:**
وقتی تنظیم «تایید خودکار نظرات» فعال باشد، بک‌اند HTML کامنت تازه را برمی‌گرداند تا جاوااسکریپت آن را به DOM اضافه کند. `render_single_comment_html` با الگوی زیر رندر می‌شود:

```php
ob_start();
?>
        <div class="flex gap-3 md:gap-4 items-start user-comment" ...>
```

خروجی `ob_get_clean()` قبل از `<div>` شامل چند کاراکتر فاصله (whitespace) است. در سمت جاوااسکریپت:

```js
const parser = new DOMParser();
const doc = parser.parseFromString(data.html, 'text/html');
const newCommentNode = doc.body.firstChild;   // یک Text Node خالی از جنس whitespace، نه <div>!
commentsList.appendChild(newCommentNode);      // یک نود متنی خالی اضافه می‌شود
newCommentNode.scrollIntoView({...});          // Text Node متد scrollIntoView ندارد → TypeError
```

چون `doc.body.firstChild` یک **Text Node** (فاصله خالی) است نه المنت `<div>`، خط `scrollIntoView` یک `TypeError` پرتاب می‌کند. این خطا داخل `.then()` رخ می‌دهد و توسط `.catch()` انتهای زنجیره fetch گرفته می‌شود، در نتیجه:
- کامنت واقعی هرگز به لیست اضافه نمی‌شود (فقط یک نود خالی اضافه می‌شود).
- تولباری با متن «خطا در اتصال به سرور» نمایش داده می‌شود — درست بعد از توست موفقیت‌آمیزِ «دیدگاه شما ثبت شد»! (پیام گمراه‌کننده و متناقض)
- `resetForm()` هرگز اجرا نمی‌شود چون بعد از خط خطا قرار دارد، پس فیلدهای فرم پاک نمی‌شوند و کاربر ممکن است دوباره سابمیت کند (ریسک ثبت کامنت تکراری).

**اثر:** این باگ روی مهم‌ترین قابلیت تبلیغ‌شده افزونه (نمایش آنی دیدگاه پس از تایید خودکار) در تمام مرورگرها ۱۰۰٪ تکرارپذیر است.

**راه‌حل پیشنهادی:** به‌جای `doc.body.firstChild` از اولین *element* استفاده شود:
```js
const newCommentNode = doc.body.querySelector('.user-comment') || doc.body.firstElementChild;
```

### ✅ B-2 (رفع شد): عدم استفاده از `wp_unslash()` قبل از `sanitize_*` روی ورودی‌های کاربر

**فایل‌ها:** `src/Security/Validator.php:27,34,42` و `src/Admin/Controllers/SettingsController.php` (چند AJAX handler، مثلاً خطوط ۳۳۸-۳۴۰)

> **وضعیت:** در تمام نقاط زیر `wp_unslash()` قبل از `sanitize_text_field()`/`sanitize_textarea_field()` اضافه شد: `Validator.php` (name, phone, comment)، `Front/Controller.php` (type واکنش)، و `SettingsController.php` (bot_token, chat_id, status در دو handler، comment پاسخ ادمین، user_name/user_phone/comment_text در ویرایش دیدگاه). در `save_settings_ajax` کل آرایه `$input = wp_unslash($_POST['md_comments_settings'])` یک‌جا unslash شد تا همه کلیدهای داخلش (title_name, telegram_webhook, bale_bot_token, ...) هم پوشش داده شوند.

**توضیح:** وردپرس به‌صورت خودکار روی `$_POST`/`$_GET` مقادیر را `addslashes()` می‌کند (magic quotes emulation). طبق استاندارد خود وردپرس، قبل از هر `sanitize_text_field()`/`sanitize_textarea_field()` باید `wp_unslash()` صدا زده شود. این کار در هیچ‌کدام از نقاط ورودی افزونه انجام نشده:

```php
$name = isset( $_POST['name'] ) ? sanitize_text_field( $_POST['name'] ) : '';
```

**اثر:** اگر کاربر در نام یا متن دیدگاه از آپاستروف/کوتیشن استفاده کند (مثلاً `O'Brien` یا نقل‌قول داخل متن)، در دیتابیس به‌صورت `O\'Brien` (با بک‌اسلش اضافه) ذخیره و نمایش داده می‌شود.

**راه‌حل:** همه‌جا الگوی `sanitize_text_field( wp_unslash( $_POST['x'] ) )` رعایت شود.

### ✅ B-3 (رفع شد): عدم اعتبارسنجی دامنه مقادیر در `edit_comment_ajax`

**فایل:** `src/Admin/Controllers/SettingsController.php:337-356`

> **وضعیت:** سه چک اضافه شد: `rating` باید بین ۱ تا ۵، `avatar_id` باید بین ۱ تا ۴ و `status` باید در `['approved','hold']` باشد؛ در غیر این‌صورت `wp_send_json_error` برگردانده می‌شود (هماهنگ با `Validator` و `change_comment_status_ajax`).

**توضیح:** برخلاف `Validator::validate_comment_submission()` که `rating` (۱-۵) و `avatar` (۱-۴) و `status` را محدود می‌کند، متد ویرایش ادمین این محدودیت‌ها را ندارد:
- `status` فقط `sanitize_text_field` می‌شود ولی هیچ‌جا با `in_array(['approved','hold'])` چک نمی‌شود (برخلاف `change_comment_status_ajax` که این چک را دارد).
- `rating` و `avatar_id` بدون کلمپ کردن به بازه مجاز مستقیم `intval` و ذخیره می‌شوند.

**اثر:** مقدار نامعتبر در دیتابیس ذخیره می‌شود که می‌تواند رندر ستاره‌ها/آواتار در فرانت را به‌هم بریزد. ریسک امنیتی مستقیم ندارد (چون این اندپوینت به `manage_options` محدود است) اما با اصل «Zero-Trust» که در مستندات پروژه ادعا شده هم‌خوانی ندارد.

**فایل:** `src/Admin/Controllers/SettingsController.php:311`

> **وضعیت:** به `\MDCustomComments\Security\Validator::get_ip_address()` تغییر یافت تا با بقیه پروژه یکسان باشد.

**توضیح:** در `reply_comment_ajax` به‌جای فراخوانی `Validator::get_ip_address()` (که هدرهای پراکسی را هم بررسی و اعتبارسنجی می‌کند)، مستقیم از `$_SERVER['REMOTE_ADDR']` استفاده شده. کار می‌کند ولی الگوی واحدی برای گرفتن IP در کل پروژه رعایت نشده.

### ✅ B-5 (رفع شد): کد مرده / ناسازگار برای واکنش (لایک/دیسلایک) کاربران مهمان

**فایل‌ها:** `src/Database/CommentRepository.php:196-208`، `src/Front/Controller.php:50-52`، `assets/front/front.js:288-294`

> **وضعیت:** شاخه‌ی IP-based حذف شد. `CommentRepository::react()` حالا صراحتاً با `if ($user_id <= 0) return false;` محدودیت لاگین را به‌عنوان دفاع در عمق در خود لایه دیتابیس هم اعمال می‌کند (نه فقط در Controller/JS)، و کوئری «بررسی واکنش قبلی» فقط بر اساس `user_id` است.

**توضیح:** متد `CommentRepository::react()` یک مسیر کامل برای کاربران مهمان (شناسایی با IP) دارد:
```php
if ( $user_id > 0 ) { ... } else {
    $existing = $wpdb->get_row(... "AND user_id = 0 AND ip_address = %s" ...);
}
```
اما هم `Front\Controller::handle_reaction()` و هم `front.js` قبل از ارسال درخواست، لاگین بودن کاربر را الزامی کرده‌اند (`is_user_logged_in()` در PHP، `userLoggedIn` در JS). یعنی شاخهٔ IP-based هرگز اجرا نمی‌شود؛ یا باید قابلیت واکنش مهمان‌ها رسماً حذف شود (و کد مرده پاک شود)، یا اگر قرار است در آینده فعال شود باید مستند و تست گردد.

### ✅ B-6 (رفع شد): شرایط مسابقه (Race Condition) در ثبت لایک/دیسلایک

**فایل‌ها:** `src/Database/CommentRepository.php:172-284`، `src/Core/Installer.php:34-44`

> **وضعیت:** به جدول `wp_md_comment_reactions` قید `UNIQUE KEY comment_user (comment_id,user_id)` اضافه شد (هم در schema نصب تازه و هم به‌صورت migration برای نصب‌های قدیمی‌تر که رکوردهای تکراری احتمالی‌شان قبل از افزودن قید پاک‌سازی می‌شود). چون بعد از رفع B-5 واکنش فقط برای کاربران لاگین‌شده مجاز است، کلید یکتا روی `(comment_id, user_id)` کافی است. علاوه بر آن، در شاخه‌ی «ثبت واکنش جدید» نتیجه `$wpdb->insert()` چک می‌شود؛ اگر به‌خاطر برخورد با قید یکتایی (یک درخواست هم‌زمان دیگر) درج ناموفق شود، شمارنده لایک/دیسلایک دستکاری نمی‌شود و وضعیت واقعی از دیتابیس خوانده می‌شود (جلوگیری از انحراف شمارنده). شماره نسخه افزونه به ۱.۱.۱ ارتقا یافت تا migration روی نصب‌های موجود اجرا شود.

**توضیح:** منطق `react()` از الگوی «چک وجود → درج/آپدیت» استفاده می‌کند بدون قید یکتایی (Unique Constraint) روی `(comment_id, user_id)` یا `(comment_id, ip_address)` در جدول `wp_md_comment_reactions`. دو درخواست هم‌زمان (مثلاً دابل‌کلیک سریع یا دو تب باز) می‌توانند هر دو از چک `$existing` عبور کرده و دو ردیف واکنش برای یک کاربر/کامنت درج شود؛ نتیجه: شمارنده لایک/دیسلایک با تعداد واقعی واکنش‌ها ناهم‌خوان می‌شود و undo/toggle درست کار نمی‌کند.

**راه‌حل:** افزودن `UNIQUE KEY (comment_id, user_id, ip_address)` مناسب (یا دو ایندکس یکتای جدا برای کاربر لاگین/مهمان) و استفاده از `INSERT ... ON DUPLICATE KEY UPDATE` یا قفل تراکنشی.

### ✅ B-7 (رفع شد): `sslverify => false` هنوز در مسیر بله باقی مانده

**فایل‌ها:** `src/Events/Listeners/SendBale.php:61`، `src/Admin/Controllers/SettingsController.php:193`

> **وضعیت:** هر دو نقطه (`SendBale::send_request` و `test_bale_connection_ajax`) دیگر `sslverify => false` را ست نمی‌کنند؛ حالا مثل Telegram/Slack به پیش‌فرض `wp_remote_post` (یعنی `true`) متکی هستند. `docs/bale-connection.md` هم به‌روزرسانی شد. **نکته برای محیط dev محلی:** اگر در محیط لوکال (مثل Local by Flywheel) درخواست به `tapi.bale.ai` با خطای گواهی SSL مواجه شد، این معمولاً یک مشکل شناخته‌شده در باندل CA محلی PHP/cURL است، نه ایرادی از افزونه — راه‌حل آن تنظیم صحیح گواهی‌ها در محیط لوکال است، نه غیرفعال‌کردن مجدد `sslverify` در کد تولید.

**توضیح:** طبق C-1 در `docs/security-report.md`، تایید SSL برای درخواست‌های به بله غیرفعال است. بررسی کد فعلی نشان می‌دهد **Telegram و Slack دیگر این مشکل را ندارند** (پیش‌فرض `sslverify=true` رعایت شده)، ولی دو نقطه مربوط به بله (ارسال واقعی پیام + دکمه «تست اتصال») هنوز `sslverify => false` دارند. یعنی گزارش امنیتی روی این مورد به‌روز نیست و مشکل هنوز عملاً باقی است (فقط محدودتر از چیزی که آن گزارش گفته).

## ۲. گلوگاه‌های کارایی (Bottlenecks)

### ✅ P-1 (رفع شد): مشکل N+1 Query در بارگذاری دیدگاه‌ها

**فایل:** `src/Database/CommentRepository.php:52-77` (`get_approved_comments`)

> **وضعیت:** به یک کوئری واحد (`WHERE post_id = %d AND status = 'approved'`، بدون فیلتر `parent_id`) تبدیل شد؛ گروه‌بندی نظرات اصلی/پاسخ‌ها و رعایت ترتیب (اصلی‌ها جدیدترین‌اول، پاسخ‌ها قدیمی‌ترین‌اول) در PHP انجام می‌شود. برای پستی با ۵۰ دیدگاه، تعداد کوئری از ۵۱ به ۱ کاهش یافت.

```php
foreach ( $comments as &$comment ) {
    $reply_query = $wpdb->prepare("SELECT * FROM {$this->table_name} WHERE parent_id = %d ...", $comment['id']);
    $comment['replies'] = $wpdb->get_results( $reply_query, ARRAY_A );
}
```

برای هر کامنت اصلیِ یک پست، یک کوئری جداگانه برای گرفتن پاسخ‌هایش اجرا می‌شود. برای پستی با ۵۰ دیدگاه اصلی یعنی ۵۱ کوئری روی هر بار نمایش شورت‌کد (بدون هیچ کش). این هم روی هر بازدید صفحه اجرا می‌شود (فرانت است، نه ادمین).

**راه‌حل:** یک کوئری واحد با `WHERE post_id = %d AND status='approved'` بدون فیلتر روی `parent_id` بزنید و گروه‌بندی پاسخ زیر والد را در PHP با یک حلقه (map بر اساس `parent_id`) انجام دهید.

### ✅ P-2 (رفع شد): عدم صفحه‌بندی (Pagination) در پنل مدیریت نظرات

**فایل:** `src/Database/CommentRepository.php:113-120` (`get_all_comments_for_admin`)، مصرف‌شده در `SettingsController::get_admin_comments_ajax`

> **وضعیت:** `get_all_comments_for_admin()` حالا `page`/`per_page` می‌گیرد (پیش‌فرض ۲۰ در هر صفحه، سقف ۱۰۰) و با `LIMIT`/`OFFSET` + یک `SELECT COUNT(*)` جدا خروجی `{items, total, page, per_page, total_pages}` برمی‌گرداند. `get_admin_comments_ajax` پارامتر `page` را از `$_POST` می‌خواند و پاس می‌دهد. در Alpine.js state (`commentsPage`, `commentsTotalPages`, `commentsTotal`) و دکمه‌های «صفحه قبل/بعد» زیر جدول اضافه شد؛ عملیات‌های تغییر وضعیت/حذف/پاسخ/ویرایش هم بعد از اتمام همان صفحه جاری را دوباره می‌خوانند (`fetchComments(this.commentsPage)`) نه همیشه صفحه اول را.

```php
$query = "SELECT c.*, p.post_title FROM {$this->table_name} c LEFT JOIN {$wpdb->posts} p ... ORDER BY c.created_at DESC";
```

هیچ `LIMIT`/`OFFSET` یا صفحه‌بندی سمت سرور وجود ندارد؛ با هر بار کلیک روی تب «مدیریت نظرات» **تمام** رکوردهای جدول (به‌همراه JOIN با `wp_posts`) یک‌جا در قالب JSON به مرورگر ارسال می‌شود. با رشد تعداد دیدگاه‌ها (چند هزار رکورد) این هم فشار روی DB و هم حجم پاسخ AJAX و هم رندر جدول در Alpine.js (که `x-for` روی کل آرایه اجرا می‌کند) را به‌شدت افزایش می‌دهد.

**راه‌حل:** افزودن پارامتر `page`/`per_page` به `get_admin_comments_ajax` + `LIMIT` در کوئری، و صفحه‌بندی در UI.

### ✅ P-3 (رفع شد): عدم صفحه‌بندی/Lazy-load در فرانت‌اند

**فایل:** `src/Front/View.php:24-26`

> **وضعیت:** `View::render()` حالا فقط اولین ۱۰ دیدگاه اصلی را می‌گیرد (`View::COMMENTS_PER_PAGE`) و در صورت وجود دیدگاه بیشتر، دکمه «نمایش دیدگاه‌های بیشتر» رندر می‌شود. یک اکشن AJAX جدید (`md_load_more_comments` در `Front/Controller.php`) صفحات بعدی را با همان کوئری بدون N+1 (`WHERE parent_id IN (...)`) برمی‌گرداند و `front.js` نتیجه را با `doc.body.children` (نه `firstChild`، برای پرهیز از باگ مشابه B-1) به لیست اضافه می‌کند و در انتها دکمه را حذف می‌کند.

### ✅ D-12 (رفع شد، یافته اضافه): فایل کامپایل‌شده `assets/front/front.css` نسبت به سورس واقعی Stale بود

هنگام اجرای `npm run build` برای تست build ادمین (P-4)، مشخص شد که `assets/front/front.css` چک‌این‌شده در گیت با کانفیگ فعلی `tailwind.config.js` هم‌خوان نیست: بازسازی آن با `npm run build:front` تعداد کلاس‌های CSS را از ۷۳۸ به ۳۸۶ کاهش داد. بررسی دقیق نشان داد ۳۵۶ کلاس حذف‌شده (مثل `touch-pan-x`, `backdrop-blur`, `text-balance`, `table-row-group`) هیچ‌کدام در `View.php` یا `front.js` فعلی استفاده نمی‌شوند (به‌احتمال زیاد باقی‌مانده از یک کانفیگ محتوای گسترده‌تر یا مارک‌آپ قدیمی‌تر است) — یعنی فایل چک‌این‌شده اصلاً هیچ‌وقت پس از تغییرات بعدی template دوباره build نشده بود. مهم‌تر، فایل قدیمی کلاس‌های جدیدی که برای دکمه «نمایش دیدگاه‌های بیشتر» (P-3) لازم بودند (`py-2.5`, `hover:border-gold`, `hover:text-gold`, `mt-6`) را نداشت — یعنی بدون rebuild، آن دکمه در سایت واقعی بی‌استایل نمایش داده می‌شد.

> **وضعیت:** `front.css` با `npm run build:front` بازسازی و commit آماده شد. پوشش کامل کلاس‌های واقعاً استفاده‌شده در `View.php`/`front.js` به‌صورت خودکار بررسی شد (استخراج تمام مقادیر `class="..."` + آرگومان‌های `classList.add/remove` و تطبیق با CSS تولیدشده) — هیچ کلاس واقعاً مورد استفاده‌ای جا نیفتاده. **توصیه:** بعد از هر تغییر در `src/Front/View.php` حتماً `npm run build` (که حالا هم فرانت هم ادمین را می‌سازد) اجرا و خروجی commit شود؛ در غیر این‌صورت این drift دوباره تکرار می‌شود.

### ✅ D-13 (رفع شد، یافته اضافه): فایل `docs/docs.txt` یک پیش‌نویس منسوخ و گمراه‌کننده بود

**فایل:** `docs/docs.txt` (حذف شد)

در حین بررسی D-6، یک فایل مستندات دیگر (`docs/docs.txt`) پیدا شد که ظاهراً پیش‌نویس اولیه معماری بوده و کاملاً با `docs/architecture.md` (نسخه واقعی و به‌روز) هم‌پوشانی داشت، اما به کلاس‌ها/فایل‌هایی اشاره می‌کرد که هرگز در پروژه پیاده‌سازی نشدند (`composer.json`, `webpack.mix.js`, `RatingRepository.php`, `Nonce.php`, `RateLimiter.php`, `CommentsController.php`, reCAPTCHA v3, REST API endpoint، کتابخانه SVG Sanitizer). نگه‌داشتن این فایل ریسک گمراه‌کردن توسعه‌دهنده بعدی را داشت (فکر کند این فایل‌ها باید وجود داشته باشند یا قرار است اضافه شوند).

> **وضعیت:** فایل حذف شد؛ `docs/architecture.md` تنها منبع معتبر معماری باقی می‌ماند.

### ✅ D-11 (رفع شد): فایل `.gitignore` با انکودینگ نادرست ذخیره شده

**فایل:** `.gitignore`

> **وضعیت:** بررسی دقیق‌تر نشان داد مشکل عمیق‌تر از صرفاً انکودینگ بود: نسخه‌ی commit-شده (`HEAD`) از قبل UTF-16 بود (`node_modules/`, `.DS_Store`, `Thumbs.db`, `*.log`)، و نسخه‌ی working-tree که قبل از این جلسه تغییر کرده بود (`M .gitignore` در ابتدای session) عملاً **کاملاً خالی شده بود** — فقط ۲ بایت BOM بدون هیچ محتوایی. این تغییر از قبل از این گفتگو روی دیسک وجود داشت؛ من آن را ایجاد نکرده بودم. فایل با همان ۴ قانون قبلی و انکودینگ UTF-8 خالص (بدون BOM) بازنویسی شد. **نکته:** یک بار تلاش اول برای بازنویسی با ابزار Write هم به‌طور غیرمنتظره‌ای UTF-16 تولید کرد (به نظر می‌رسد مختص همین نام فایل/محیط ویندوز بود)؛ در نهایت با نوشتن مستقیم بایت‌ها از طریق PowerShell (`[System.IO.File]::WriteAllText` با `UTF8Encoding($false)`) درست شد. توصیه می‌شود قبل از commit کردن، `cat .gitignore` یا `file .gitignore` را یک‌بار دیگر چک کنید تا مطمئن شوید ادیتور شما دوباره آن را UTF-16 ذخیره نکرده.

فایل با انکودینگی (احتمالاً UTF-16 با BOM) ذخیره شده که گیت آن را «باینری» تشخیص می‌دهد (`git diff` قابل خواندن نیست، خروجی `cat` هم کاراکترهای garbled نشان می‌دهد). باید با انکودینگ UTF-8 (بدون BOM) دوباره ذخیره شود تا دیف‌های آینده قابل بررسی باشند.
