سند معماری افزونه مدیریت نظرات سفارشی (MD-Custom-Comments)
۱. معماری کلی: رویکرد هیبریدی (MVC + EDA)
هسته افزونه بر اساس اصول شی‌گرایی (OOP) و الگوی MVC برای مدیریت داده‌ها و رندرینگ ساخته می‌شود، اما برای رفتارهای سیستمی (ارسال پیام، هوک‌های شخصی‌سازی) از معماری مبتنی بر رویداد (EDA) با استفاده از سیستم Actionهای وردپرس استفاده می‌کنیم.

مزیت: کدهای CRUD (ذخیره، خواندن، آپدیت، حذف) به شدت قابل پیش‌بینی و قابل تست (MVC) هستند، در حالی که افزودن پیام‌رسان‌های جدید در آینده بدون دستکاری کدهای هسته امکان‌پذیر است (EDA).

۳. استراتژی بارگذاری شرطی (Conditional Asset Loading)
دغدغه اصلی: لود نشدن فایل‌های CSS و JS افزونه در کل سایت.
راه‌حل معماری:

در کلاس Front/Assets.php و Front/Shortcode.php به این شکل عمل می‌کنیم:

شناسایی شورت‌کد قبل از لود اسکریپت‌ها:
php

public function should_load_assets() {
public function should_load_assets() {
    global $post;
    if ( is_a( $post, 'WP_Post' ) && has_shortcode( $post->post_content, 'md_comments' ) ) {
        return true;
    }
    return false;
}
لود در فوتر: تمام فایلهای JS و CSS باید با پارامتر in_footer = true لود شوند.
استراتژی Tailwind CSS (حیاتی):
به هیچ وجه فایل کامل Tailwind را لود نکنید. از ابزارهایی مثل Laravel Mix یا Vite استفاده کنید که در زمان Build، فایل‌های View افزونه را اسکن می‌کند و فقط کلاس‌های استفاده شده (Purged CSS) را در یک فایل front.min.css خروجی می‌دهد. حجم نهایی CSS باید زیر ۱۰ کیلوبایت باشد.
۴. استراتژی امنیت (Zero-Trust Security)
امنیت باید در دو لایه فرانت‌اند و بک‌اند پیاده‌سازی شود:

الف) امنیت فرانت‌اند (Frontend Security)
Honeypot Field: یک فیلد مخفی با display:none و aria-hidden="true" (مثلاً name="md_hp_website"). اگر این فیلد در درخواست ایجاکس پر شده بود، درخواست در سمت سرور Silently رد می‌شود (بدون پیام خطا تا ربات متوجه نشود).
reCAPTCHA v3: لود اسکریپت گوگل فقط در صفحاتی که شورت‌کد وجود دارد. ارسال توکن گوگل همراه با درخواست ایجکس.
Nonce Token: چاپ یک متغیر جاوااسکریپت حاوی wp_create_nonce('md_submit_comment') به صورت inline در صفحه.
ب) امنیت بک‌اند (Backend Security)
Validation & Sanitization (اعتبارسنجی و پاک‌سازی):
قانون طلایی: هرگز به داده‌ای که از سمت کاربر (یا ادمین) می‌آید اعتماد نکنید.
شماره موبایل: sanitize_text_field + چک کردن Regexایران (/^09[0-9]{9}$/).
متن کامنت: wp_kses_post (اجازه دادن به تگ‌های مجاز) یا اگر پشتیبانی HTML نمی‌خواهید sanitize_textarea_field.
SQL Injection: استفاده مطلق از $wpdb->prepare() در کلاس‌های Repository. هیچ متغیری مستقیم در کوئری وارد نشود.
Rate Limiting: استفاده از Transients API وردپرس. ذخیره IP کاربر به مدت ۶۰ ثانیه. اگر درخواست تکراری بود، با خطای 429 جلوگیری شود.
امنیت SVG (برای ستاره‌ها و آواتارهای پنل ادمین): ذخیره کدهای SVG در دیتابیس خطرناک است. حتماً از کتابخانه enshrined/svg-sanitize در کامپوزر استفاده شود تا تگ‌های <script> و onload از داخل SVG حذف شوند.
Direct Access Prevention: در ابتدای تمام فایل‌های PHP:
defined( 'ABSPATH' ) || exit;

۵. معماری دقیق پنل ادمین (Admin Panel)
پنل ادمین باید بر اساس WordPress Settings API ساخته شود، اما برای سرعت و تجربه کاربری (UX) بهتر، فرم‌ها را با AJAX پردازش می‌کنیم تا صفحه رفرش نشود. از Alpine.js برای تعاملات UI پنل ادمین (مثل تب‌ها و آپلودر) استفاده کنید.

تب ۱: تنظیمات فرم و ظاهر (Form Settings)
بخش آواتارها: یک ریپیتر (Repeater) حاوی ۴ فیلد آپلود تصویر (استفاده از wp.media وردپرس). فقط شناسه پیوست (Attachment ID) ذخیره می‌شود.
بخش ستاره‌ها (SVG): یک <textarea> با زبان CodeMirror (که وردپرس آن را دارد) برای وارد کردن کد SVG. هنگام ذخیره، داده از طریق کلاس امنیتی SVG Sanitizer عبور می‌کند.
بخش تایتل فیلدها: فیلدهای متنی ساده برای تغییر نام "نام و نام خانوادگی" و "شماره همراه". ذخیره در wp_options به صورت آرایه سریالیزه شده.
تب ۲: مدیریت نظرات (Comments Management)
معماری: به جای استفاده از جدول پیش‌فرض وردپرس (WP_List_Table) که بسیار کند و غیرقابل شخصی‌سازی است، یک رابط اختصاصی بسازید.
پیاده‌سازی: یک Custom Endpoint با WP REST API بسازید (مثلاً /wp-json/md/v1/comments). در فرانت‌اند ادمین، با جاوااسکریپت (Alpine.js یا Vue) داده‌ها را Fetch کنید و در یک جدول مدرن (Tailwind) رندر کنید.
اطلاعات هر ردیف: نام کاربر، شماره موبایل، آواتار انتخاب شده (رندر تصویر)، امتیاز ستاره‌ای (رندر ستاره‌های رنگی)، متن کامنت، و نام پست (لینک شده به پست).
پاسخ ادمین: یک دکمه Modal باز می‌کند. ادمین پاسخ می‌نویسد، به ریست ای‌پی‌آی ارسال می‌شود. در بک‌اند، پاسخ به عنوان یک کامنت با comment_parent = ID کامنت اصلی ثبت می‌شود.
تب ۳: تنظیمات پیام‌رسان‌ها (Messenger Integrations)
فیلدها:
وضعیت (فعال/غیرفعال)
وب‌هوک URL (اعتبارسنجی شود که حتماً با https شروع شود).
رویداد (EDA Implementation):
هنگامی که کامنت در دیتابیس ذخیره شد، در کلاس Repository:
php

do_action( 'md_comment_inserted', $comment_id, $comment_data );
کلاس‌های SendTelegram و SendSlack به این اکشن هوک می‌شوند:
php

add_action( 'md_comment_inserted', [ $this, 'dispatch' ], 10, 2 );
پردازش پس‌زمینه (Async Processing):
برای جلوگیری از کندی سرعت ثبت کامنت کاربر، ارسال وب‌هوک نباید Sync باشد. از WP Action Scheduler (که ووکامرس آن را توسعه داده و روی اکثر سایت‌ها نصب است) استفاده کنید. در لیستنر وب‌هوک، به جای ارسال مستقیم با wp_remote_post، یک اکشن زمان‌بندی شده ثبت کنید:
php

as_schedule_single_action( time(), 'md_send_webhook_event', [ 'platform' => 'telegram', 'data' => $comment_data ] );
این کار باعث می‌شود کاربر در کسری از ثانیه پیام موفقیت آمیز را ببیند و وب‌هوک در پس‌زمینه سرور پردازش شود.
۶. معماری رندر فرانت‌اند و AJAX
برای رعایت اصول سئو و سرعت (LCP/FCP):

رندر اولیه (SSR): فرم و کامنت‌های تایید شده باید در سمت سرور (PHP) رندر شوند و همراه با HTML اصلی صفحه لود شوند (داخل شورت‌کد). این کار برای گوگل و سرعت اولیه عالی است.
ثبت نظر (AJAX): دکمه ارسال، فرم را از طریق fetch API به admin-ajax.php (یا ریست ای‌پی‌آی) می‌فرستد.
پاسخ سرور: سرور کامنت را با وضعیت hold (یا approve بسته به تنظیمات) ذخیره می‌کند و یک بلوک HTML تمیز (از فایل View) برمی‌گرداند.
داینامیک کردن DOM: جاوااسکریپت دریافتی را به انتهای لیست کامنت‌ها append می‌کند و فرم را پاک می‌کند. هیچ نیاز به ری‌اکت یا ویو در فرانت‌اند سایت نیست (Vanilla JS کافی و بهینه‌ترین است).
